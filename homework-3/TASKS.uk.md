# Домашня робота 3: Специфікація на основі проєктування

## Огляд

Розробіть **пакет специфікацій** для фінансово-орієнтованого застосунку. Ви створюєте лише документи: багаторівневу специфікацію, правила для агентів та README, що пояснює ваші рішення та галузеві практики. **Реалізація коду не потрібна.**

Оцінюваним артефактом є **сама специфікація**: наскільки чітко ви декомпозуєте проблему, наскільки прослідковувані вимоги від цілей до задач, і наскільки добре ви передбачаєте режими відмов, верифікацію та нефункціональні очікування.

---

## Навчальні цілі

Виконавши цю домашню роботу, ви зможете:

- Структурувати **кілька рівнів** наміру: бачення / ціль верхнього рівня → цілі середнього рівня → нотатки з реалізації → явний початковий/кінцевий контекст → низькорівневі, виконувані задачі
- Визначати конфігурацію агента (`agents.md`), щоб AI-партнер з кодування поводився послідовно у вашій предметній галузі
- Фіксувати проєктні конвенції у правилах Copilot, файлах `.md` Claude Code або правилах Cursor
- Відображати найкращі практики FinTech/банківської справи у вашій специфікації (відповідність нормативам, безпека, аудит, обробка даних)
- Кодувати **крайові випадки**, очікування щодо **верифікації** та цілі **продуктивності** (або іншого типу SLO) як повноцінні частини специфікації — а не як другорядні думки

## Завдання

### Вимоги до проєкту (лише верхній рівень)

Ви обираєте обсяг і глибину; пункти нижче навмисно широкі, щоб ви **уточнили та звузили** їх у своїй специфікації.

- **Предметна галузь**: Фінансово-орієнтований застосунок — наприклад, **життєвий цикл віртуальної картки** (створення, заморозка/розморозка, встановлення лімітів, перегляд транзакцій) або інша невелика фінансова функція на ваш вибір (ліміти витрат, заміна картки, сповіщення, прийом спорів тощо).
- **Зацікавлені сторони**: Передбачте щонайменше **кінцевих користувачів** та **внутрішній операційно-комплаєнсний** погляд. За бажанням можна додати інших (підтримка, фрод, фінанси), якщо це підвищить реалістичність.
- **Обмеження**: Система має бути придатною для **регульованого** середовища: аудитованість, безпека та чіткі межі для чутливих даних. Ви вирішуєте, наскільки суворими і **де** кожна вимога з'являється у специфікації (цілі vs. нотатки з реалізації vs. критерії прийняття на рівні задачі).
- **Поза рамками цієї домашньої роботи**: Реальний код, API або UI. Потрібні лише письмова специфікація та супутні документи (`agents.md`, правила, `README.md`).

Використовуйте ці пункти як **вихідні вимоги**; ваше завдання — перетворити їх на **конкретну, багаторівневу, виконувану** специфікацію та обґрунтувати свої рішення в README.

### Що означає «глибина» для `specification.md`

Ваш `specification.md` має читатися як документ, за яким інженерна команда (та AI-агент) могли б працювати **без здогадок**. Прагніть до **багатого нашарування**, а не до довгої прози заради неї самої.

| Шар | Призначення | Що включати (мінімальна планка) |
|-----|-------------|--------------------------------|
| **Ціль верхнього рівня** | Полярна зірка | Одне чітке формулювання результату для користувача/бізнесу; межа обсягу в одному реченні |
| **Цілі середнього рівня** | Перевіряємо «що» | Кілька цілей, які **спостерігаються** (що змінюється у світі, коли це вдається?) |
| **Нефункціональні вимоги та політики** | Наскільки добре / наскільки безпечно | Очікування щодо безпеки, приватності, аудиту/логування, **надійності** та **продуктивності або бюджетів затримки** де релевантно — формульовані як цілі або діапазони, а не розмите «має бути швидким» |
| **Нотатки з реалізації** | Обмеження для будівничих | Правила обробки даних, ідемпотентність, семантика помилок, форматування грошей/ID, конвенції, які агент не повинен порушувати |
| **Контекст (початок / кінець)** | Робочий простір агента | Що існує до початку роботи vs. які артефакти/стан існують після — файли, сервіси, сховища даних **як гіпотетичні**, якщо хочете, але достатньо конкретні, щоб уникнути двозначності |
| **Низькорівневі задачі** | Виконувані зрізи | Достатньо задач для **справжньої декомпозиції** (зазвичай **багато** малих задач, а не три загальні пункти). Кожна задача має посилатися на відповідну ціль середнього рівня |

**Наскрізні вимоги (мають з'явитися десь у специфікації, а не лише в README):**

1. **Крайові випадки та режими відмов**
   - Явний список або таблиця: порожні стани, часткові відмови, конкурентні дії, невалідні ліміти, застарілі дані, межі дозволів, шахрайські патерни тощо — **в рамках обраної вами функції**, а не загальний есей про безпеку.
   - Для важливих сценаріїв вкажіть **очікувану поведінку** (видимий для користувача результат + наслідки для аудиту/комплаєнсу де релевантно).

2. **Верифікація**
   - Як ви **дізнаєтесь**, що кожна ціль середнього рівня досягнута: контрольні точки перевірки, категорії тестів (юніт/інтеграційні/e2e де застосовно **як документація**), фікстури даних, перевірки звірки або кроки ручного комплаєнс-аудиту.
   - Щонайменше кілька низькорівневих задач мають завершуватися **критеріями прийняття** або **визначенням готовності**, сформульованими так, щоб виконавець міг їх відзначити.

3. **Очікувана продуктивність**
   - Визначте **вимірювані** очікування, відповідні вашій функції: наприклад, перцентилі затримки API, обмеження розміру пакетів, правила пагінації, ліміти рейтів, час узгодженості читань після записів або пропускна здатність фонового завдання.
   - Якщо числа гіпотетичні — позначте їх як **передбачувані цілі** та поясніть **чому** вони розумні для UX або операцій у FinTech.

## Результати

Ваша здача має включати такі файли в `homework-3/`:

### 1. `specification.md`

Повна специфікація продукту/функції за **багаторівневою** структурою (дивіться таблицю вище). Ви можете використовувати `specification-TEMPLATE-example.md` як початковий шаблон, але від вас очікується **вийти за рамки** мінімального шаблону: більше цілей, багатші нотатки з реалізації, повніший контекст та **суттєвий** список низькорівневих задач з деталями у стилі критеріїв прийняття, інтегрованими **крайовими випадками**, **верифікацією** та **продуктивністю** — а не зведеними до одного розмитого пункту.

### 2. `agents.md`

Рекомендації для агента/AI: припущення щодо технологічного стеку, правила предметної галузі (наприклад, банківська справа), стиль коду, **очікування щодо тестування та верифікації**, обмеження безпеки та комплаєнсу, а також **як агент має обробляти крайові випадки** (наприклад, ніколи не логувати PAN, завжди надавати перевагу ідемпотентним записам).

### 3. Правила редактора / AI

Один набір правил редактора/AI (наприклад, `.github/copilot-instructions.md`, файл `.claude/` або `.cursor/rules/*.md`), що керує тим, як AI має працювати в цьому проєкті (іменування, патерни, чого уникати, чутливі до FinTech налаштування за замовчуванням).

### 4. `README.md`

| Розділ | Зміст |
|--------|-------|
| Студент та підсумок завдання | Ваше ім'я та короткий підсумок домашньої роботи |
| Обґрунтування | Чому ця специфікація написана саме так (включно з тим, як ви обирали цілі продуктивності та глибину верифікації) |
| Найкращі галузеві практики | Які практики ви додали і **де вони з'являються** у специфікації (посилання на файл/розділ) |
